# Композиция приложения

App связывает один Project с агентским интерфейсом, серверным исполнением
и Web-интерфейсом. Его контракт определяет запуск, проверку готовности,
управляемую замену и завершение приложения. Способ выделения частей задан
в [методике проектирования](../../project/notes/design.md), общие направления
зависимостей — в [архитектуре Repo](../../repo/notes/architecture.md).

## Основные составляющие

* MCP предоставляет агентский интерфейс: инструменты, ресурсы, проверки
  аргументов, результаты и контекст запросов. App передаёт ему управляющие
  возможности; MCP не создаёт второй App и не становится владельцем сервера.
  Постоянный транспорт и исполнение актуального запроса имеют разные сроки жизни.
* Server владеет работающим HTTP/WebSocket-сервисом, каталогом Project,
  соединениями, пакетными сессиями и управлением браузерными представлениями.
  Он доставляет результаты Web и связывает сетевые запросы с их владельцами.
* Web владеет интерфейсом как целым: исполняемой страницей, её подготовкой
  и выпуском. Он согласует опубликованную оболочку с платформами открытых страниц.
  Состояние выпуска и выбор совместимых артефактов находятся у Web, а не в HTTP-обработчике.

## Части Web

Build подготавливает независимые артефакты и подтверждает их входы.
Release ведёт одну общую операцию выпуска: подготовку, запрос публикации,
наблюдение и завершение. Protocol определяет обмен готовыми сведениями Web
между процессом сервера и страницей. Page владеет жизненным циклом одной
страницы. Web соединяет эти возможности, сохраняя разные среды их исполнения.
Браузерный вход не загружает серверную реализацию Web; сервер не исполняет
код интерфейса, чтобы определить готовность его артефакта.

Page композирует Shell, Home и Package. Shell удерживает единственный
Browser Root страницы, его Document, Canvas и проекции. Home представляет
выбор предмета, Package — выбранный пакет, его документы и сценарии.
Навигация между ними принадлежит Page и сохраняет общую среду.
Подготовка адреса, связь с сервером, сообщения состояния, инспекция агента
и подключение авторских стилей относятся к этой странице и размещаются у неё.

Shell соединяет рабочую область, окна и управление ViewPoint в одном Experience.
Workbench владеет своим состоянием, событиями, областями просмотра и Inspector;
его каталог является принадлежащей ему частью. Minimap получает снимок
публичной рабочей области для HUD, а окно MCP показывает запросы и ответы.
Окна владеют собственными настройками и восстановлением допустимых значений.
Shell предоставляет хранение и перенос пользовательского состояния между
выпусками, не дублируя правила начальной раскладки каждого окна.

Внутренние состояния, начальные значения и вспомогательные функции остаются
в реализации соответствующего владельца. Тестовая подмена Browser Root
относится к средствам проверки, а не к составу рабочего интерфейса.

## Подготовка и время жизни

Изменение браузерной части не меняет исполняемый граф серверного процесса.
Платформа, Web-интерфейс и пакеты проекта подготавливаются отдельными операциями.
Выпуск Web использует обычный Bun.build с JSX-плагином и готовой платформой;
пакетные сессии используют опубликованную среду Storybook.
Обновление оболочки не пересобирает пакет пользователя и не создаёт для панели
или сценария отдельный Experience.

Владельцы публикации, доставки и применения различны. Web публикует согласованный
набор immutable артефактов; Server передаёт сведения об обновлении; Page применяет
новую реализацию с сохранением или восстановлением своей среды. Успешная
публикация не является подтверждением показанной версии. Точные гарантии
подготовки принадлежат [Build](../web/build/notes/compilation.md), а сохранение
процесса и его authority — [жизненному циклу App](./lifecycle.md).

## Сохранность при переносе

Изменение физического положения сохраняет самостоятельную identity пакета.
Внешние потребители продолжают получать возможность целого; внутренняя часть
не становится их новым владельцем только вследствие переноса исходника.
Перенос также учитывает сохранённые адреса, истории чатов и контекст ACP.
Совпадение нового имени или каталога не разрешает объединять разные истории.
Работающие экземпляры, сохранённые артефакты и новые исходники проверяются
как разные участники перехода.
