# Предложения по улучшению сборки Web

## Подробность длительной компиляции

- [ ] Сделать наблюдаемой фактическую работу внутри стадии `host`.

**Основание.** Пересборка Web при проверке журналов MCP 4 октября 2026 года
заняла 557 109 мс. Большую часть ожидания статус показывал `host`, загрузку
процесса и `cache.status: unknown`. Эти данные не устанавливают причину
длительности и сами по себе не доказывают избыточную компиляцию.

**Почему здесь.** [Сборщик Web](src/browser-build.ts) задаёт входы и границы
стадии `host`; [worker](src/builder.ts) уже передаёт её прогресс в общую очередь.
Физических владельцев и compiler plugins предоставляет
[Tech Build Compiler](../../../tech/build/compiler/index.ts).

**Предложение.** Передавать по существующему каналу прогресса фактический
обрабатываемый модуль и его владельца, длительность и объём выполненной работы.
Показывать повторное использование результата и причину повторной подготовки
там, где это действительно известно. Измерения компилятора получать через его
публичный контракт; Web только связывает их со своей операцией. Не добавлять
опрос файлов или вымышленные проценты завершения. Оптимизацию выбирать после
измерений холодной сборки, повтора без изменений и изменения одного компонента.

**Проверка готовности.** При задержке одного модуля статус называет его владельца;
параллельные операции не смешивают события. Для трёх указанных запусков доступны
сопоставимые сведения о выполненной компиляции и повторном использовании.
[Сценарии worker](test/builder.test.ts) и [сборки](test/browser-build.test.ts)
подтверждают передачу событий; [граница платформы](test/platform-boundary.test.ts)
остаётся неизменной — пересборка Web не компилирует готовую платформу.

## Связь результата с прочитанными исходниками

- [ ] Сделать проверяемым набор входов конкретной сборки при параллельных изменениях.

**Основание.** Во время работы над журналами параллельно менялись namespace
в Storybook и Immersive. Изменение исходников наблюдалось; получение смешанного
артефакта не доказано. [Receipt](src/receipt.ts) уже проверяет контрольные суммы
готовых файлов, а `hostModuleEpoch` вычисляется из outputs. Это подтверждает
целостность результата, но не объясняет, какие версии входов были прочитаны.

**Предложение.** Связать результат с точными входами, прочитанными компилятором:
исходниками, выбранными зависимостями и настройками. Сначала проверить имеющиеся
механизмы compiler/artifacts; общую фиксацию входов реализовывать у технического
владельца, а Web сохраняет её свидетельство вместе со своим результатом.
При изменении входа во время работы явно отличать подтверждённый результат от
устаревшего или неопределённого. Git HEAD недостаточен для незакоммиченных правок;
новые ветки и worktree для этого не требуются.

**Проверка готовности.** Управляемая правка используемого файла посередине сборки
не выдаёт неподтверждённый набор входов за проверенную текущую версию. Правка
постороннего пакета не инвалидирует результат. Неуспешная проверка сохраняет
предыдущую опубликованную оболочку. Данные результата позволяют сопоставить
проверенную сборку с фактически использованными входами.
