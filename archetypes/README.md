# Правила структуры проектов

Этот пакет описывает общие правила, по которым Storybook читает проекты и
пакеты. Правила применяются и к визуальным, и к невизуальным пакетам.

## Явный состав проектов

Пользователь добавляет и удаляет проекты через интерфейс Storybook или MCP.
Постоянная конфигурация находится в `~/.storybook/projects.json` и содержит
только JSON-массив абсолютных путей к выбранным каталогам:

```json
[
  "/path/to/project",
  "/path/to/independent-package"
]
```

Порядок путей задаёт порядок корней. Пустой массив означает пустой каталог.
Storybook не восстанавливает состав из списка соседних репозиториев, PID,
старых запусков или кэша сборки. Повторное добавление того же каталога не
создаёт дубль. Удаление из списка не удаляет файлы проекта.

Конфигурация не содержит имён, идентификаторов, категорий и копий metadata.
Эти сведения читаются из выбранного проекта. Если удаляется вложенная ветвь
старой композиции, оставшиеся ветви сохраняются своими путями, без списка
скрытых идентификаторов и без изменения декларации владельца.

## Человекопонятное название

Корень проекта и каждый самостоятельный пакет объявляют непустой `label`
в своём `package.json`:

```json
{
  "name": "@scope/parser",
  "label": "Разбор выражений"
}
```

`name` — техническая идентичность для зависимостей и импортов. `label` —
название для человека. Изменение `label` не меняет `name` и маршруты.
Storybook читает `label` при открытии и обновлении проекта; UI и MCP используют
одно название из общего каталога. Имя не сохраняется в пользовательской
конфигурации и не выводится из имени удалённого ранее проекта.

## Структура и манифест

Репозиторий и каждый самостоятельный пакет должны иметь обзор в `README.md`
рядом со своим `package.json`. Он объясняет назначение, ответственность и
основные точки входа, а подробные контракты остаются у модулей и их тестов.
Storybook обнаруживает этот README автоматически и при наличии манифеста,
и без него; перечислять стандартный путь в JSON не требуется. Явное поле
`readme` существующего манифеста сохраняет приоритет. Отсутствующий README —
пробел документации, но не основание скрывать пакет или репозиторий.
Обзор обычной директории внутри пакета берётся только из TSDoc её `index.ts`.

Стандартный корневой README не перечисляется в манифесте. Поле `readme`
сохраняется только для явно нестандартного документа; генератор не создаёт
дублирующую ссылку на README. Пакету без каталога, runtime, авторских stylesheet,
widgets и нестандартного обзора не нужен манифест, повторяющий `package.json`.
Переход выполняется поэтапно: сначала проверяются корневой README, идентичность,
навигация и ресурсы; затем удаляется избыточная декларация. Каталоги сценариев
и действующие нестандартные настройки сохраняются до отдельной миграции.

Структура — сведения из устройства проекта и его package.json. Манифест —
явное описание содержимого в .storybook. Оба подхода передают один каталог
в UI и MCP.

Состав внутренних пакетов структурного проекта задаётся `package.json#workspaces`.
Точные каталоги, `packages/*`, `packages/**` и исключения `!packages/excluded/**`
раскрываются встроенным Bun.Glob. Порядок шаблонов сохраняется, внутри шаблона
пакеты упорядочены по пути; пересечения не создают повторных пакетов.
Каталоги без package.json не становятся пакетами. node_modules и .git
не входят в состав. Пути остаются внутри проекта; symlink-каталоги отклоняются.

Каждый найденный пакет виден и доступен для выбора, даже когда у него нет
`.storybook/manifest.json`. Имя и название читаются из package.json; при
отсутствии манифеста README.md пакета служит его описанием, если существует.
Наличие preview, TSX или графического runtime не является требованием.
Манифест пакета, если он существует, добавляет каталог, сценарии, ресурсы
и runtime. Некорректный существующий манифест даёт локальную диагностику;
его отсутствие ошибкой не является.

Проект с workspaces не повторяет состав в manifest.packages. Для прежнего
манифестного подхода без workspaces сохраняется явный список packages.
Одновременное задание обоих источников отклоняется. Корневой манифест сохраняет описание и идентификаторы владельца.
Каждый выбранный путь представлен корнем репозитория. Если в корне расположен
самостоятельный пакет, он отображается внутри репозитория и раскрывает свои
внутренние workspace-пакеты по тому же правилу, что и остальные пакеты.

Главная панель содержит дерево репозиторий → пакет → вложенный пакет. Родитель
пакета определяется ближайшим содержащим его пакетом среди обнаруженных
workspace-пакетов. Промежуточные каталоги без package.json не становятся пакетами.
Стрелка управляет раскрытием, подпись — выбором. Вторая панель показывает
категории и предметы выбранного пакета; dock — варианты выбранного предмета.
Выбор пакета открывает содержимое в текущей вкладке. Сборки, ревизии,
diagnostics и lastWorking изолированы по packageId. Агент переиспользует вкладку
своего пакета или создаёт фоновую, сохраняя остальные. Успешное применение
обновляет все вкладки этого пакета; одна сборка этого не делает.
Вложенность не создаёт зависимость сборок или право исполнять код дочернего пакета.


Предметная панель выбранного репозитория или пакета также показывает только непосредственные
обычные директории рядом с разделами `catalog.json`. Название директории берётся
из имени на диске, а обзор берётся только из начального TSDoc-блока
`@packageDocumentation` файла `index.ts` этой директории. README.md не является
источником или fallback; существующие README сохраняются. Если index.ts или
описание отсутствуют, директория остаётся видимой с явным пустым обзором.
TypeScript не исполняется. Markdown, блоки кода, @remarks и @example сохраняются
в текстовой проекции; документация классов и функций в обзор не включается.
Исходник наблюдается общим watcher; текст входит в снимок каталога и публикуется
как module.md только после проверки digest исходника. Пакетные вкладки получают
новое описание после успешной сборки и применения ревизии. Локальные ресурсы
разрешаются относительно index.ts через общий Markdown allow-list. `src`,
`.git`, `node_modules`, `.storybook`, `tests` и `test` скрыты на любой глубине. Остальные исключения
определяет Git через `git check-ignore --no-index`: учитываются вложенные
`.gitignore` и правила с `!`, включая уже отслеживаемые Git каталоги.
Имена `build` или `dist` сами по себе не являются основанием для исключения.
Пакет с `package.json` не обходится как обычная директория; состав пакетов
по-прежнему определяется workspaces или согласованной manifest-композицией.
Symlink-директории не обходятся. Пустые директории остаются видимыми.
Поддиректории этих директорий не обходятся и в каталог не добавляются.
Иерархия самостоятельно обнаруженных пакетов в главной панели сохраняется.

Directory nodes проходят через тот же нормализованный каталог, граф, поиск и
revision snapshot. Адрес директории имеет вид `/pkg-<package-slug>/dir-<name>`;
второй сегмент `dir-` не допускается. Истории JSON-каталога сохраняются
под обычными маршрутами; начальный `dir-` зарезервирован для директорий. Изменения директорий и `.gitignore`
наблюдает общий watcher. Изменение директории репозитория не меняет сборки его
пакетов. Навигация внутри пакета использует его применённую ревизию и тот же Root.


Публичный адрес пакета использует читаемый slug: `@zavx0z/dom` становится
`/pkg-zavx0z-dom/`, `@internal/visual` — `/pkg-internal-visual/`.
У имени удаляется начальный `@`, разделитель scope `/` заменяется на `-`;
имена без scope сохраняются. В URL к slug добавляется `pkg-`, а к имени
непосредственной директории — `dir-`. Настоящий packageId в declarations, imports,
сборках, ревизиях и MCP остаётся неизменным. Slug разрешается через каталог;
разные packageId с одинаковым slug отклоняются при построении графа.

Старые encoded URL распознаются по exact packageId. Применённая ревизия со
старым форматом продолжает обслуживаться по своему прежнему адресу, пока агент
не проверит и не применит новую сборку. После применения старые ссылки переходят
на новый адрес с сохранением route и preview query. Приватные адреса immutable
артефактов не переименовываются. Bootstrap получает exact packageId из native
HTML metadata; browser lifecycle подтверждает пакет через bridge/metadata,
поскольку один slug не позволяет восстановить исходное npm-имя.

Изменения состава и появление или удаление манифеста отслеживаются через
общий watcher. Идентичность существующего пакета сохраняется. Пакет владеет
своими исходниками, документацией, сценариями и проверками. Названия всех
корней и пакетов обязательны в package.json#label; label в manifest запрещён.
