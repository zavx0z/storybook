# Единая структура Project, Repo, Domain и Component

Project соединяет выбранные независимые Repo. Repo сам является Package —
корнем монорепозитория с общей Git-историей. Внутри него самостоятельные части
выражаются пакетами Domain и Component. Поддомен остаётся Domain, составной
компонент — Component. Domain не является одновременно Component.

```text
Project
├─ Package — Repo
│  └─ Package — Domain
│     ├─ Package — Domain
│     │  └─ Package — Component
│     └─ Package — Component
└─ Package — Repo
   └─ Package — Component
```

Промежуточные домены необязательны. Один Repo может входить в несколько проектов
без копии identity или исходников. Самостоятельные Repo не вкладываются друг
в друга. Наличие workspaces означает состав пакетов, а не новый класс Container.

## Владельцы норм

- [Package](../package/index.ts) — общая идентичность, состав и публичные входы.
- [Project](../project/index.ts) — композиция независимых Repo.
- [Repo](../repo/index.ts) — корневой пакет и граница Git.
- [Domain](../domain/index.ts) — предметная область и публичные пути к её частям.
- [Component](../component/index.ts) — собственная реализация поведения.
- [Specs](../specs/index.ts) — правила исполняемой документации.
- [Развитие структуры](development.md) — принадлежность и размещение частей.
- [Экспорты](../package/notes/draft-exports.md) — API области и фактический владелец кода.
- [Документация](draft-documentation.md) — описание поведения у его владельца.

Классификация не задаётся полем манифеста, именем папки или иконкой.
[Сценарий Package](../package/spec/scenario.spec.ts) один раз получает факты
из `readPackage`, раскрывает общие требования и условные разделы Repo, Domain
и Component. Разделы, примеры, пояснения `expect` и результаты одного запуска
служат проверке, документации, представлению Storybook и сведениям MCP.
Никакой отдельный классификатор не выбирает класс по имени теста или файла пакета.
Подтверждение требует полного прохождения применимых проверок сценария.

Domain не требует собственного spec: структура и exports дают данные общим
проверкам. Собственные сценарии поведения, если они есть, исполняются существующим
механизмом сценариев пакета. Читатели Repo, Domain и Component раскрывают отдельные
части тех же фактов; их собственные примеры описывают использование читателей.

Понятие предмета архетипа не совпадает с классом его читателя. Например,
`readDomain` — исполняемый Component, который читает сведения о Domain.
Файловая проверка не доказывает полноту смысла предметных правил.
Нереализованные проверки сохраняются [у Component](../component/notes/verification.md)
и не подставляются как найденные нарушения каждого проверяемого пакета.

## Поэтапный переход

Существующие пакеты и пути не перемещаются автоматически вследствие введения
стандарта. Несоответствие переходного пакета публикуется как предупреждение.
Полное прохождение стандарта и успешное применение той же ревизии автоматически
закрепляют строгий режим; последующая регрессия блокирует сборку, не переводя
пакет назад в переходный режим. Сохранением этого факта владеет lifecycle сборки,
а не авторские metadata. Технические ошибки исполнения и компиляции не становятся
успешными проверками. Исполнение сценария не меняет режим или файлы проверяемого пакета.

Самостоятельные части оформляются пакетами; дополнительных структурных классов
Entity и Category нет. Правила их прежнего размещения заменены правилами Component
и Domain, а действующее отображение обычных директорий описано как переходный механизм.
Маршруты и действующее обнаружение сохраняют своих владельцев и мигрируют отдельно.
