# Сценарии

## Чтение сценария

Публичный `readScenario({path})` запускает настоящий Bun Test и возвращает
аргументы и результаты наблюдаемых вызовов вместе с группой и названием теста.
Вход содержит только путь. Контракты принадлежат `contract/input.ts` и
`contract/output.ts`; отдельного инспектора и параллельного API нет.

Сборщик читает runtime imports сценария и ближайший package.json.
Рабочая директория — каталог этого пакета. Preload берётся из его bunfig.toml
и подходящей команды bun test в scripts.test. Shell-команды не исполняются.
Для выбора команды поддержаны явные пути и директории, без glob и shell substitutions.
JSX runtime определяется по публичному jsx-runtime export пакета preload.
Неоднозначная конфигурация приводит к ошибке, а не к выбору случайного runtime.

Функции импортированных прикладных модулей и собственные изменяемые методы
возвращённых объектов наблюдаются автоматически. Встроенные модули Bun/Node
исключены. Обёртки сохраняют исходные this и Promise; файлов сценария и
компонента на диске сборщик не меняет. Immutable методы, constructors,
динамические imports и скрытое состояние native объектов пока не поддержаны.

## Ответственности src

- `discover.ts` находит владельца и собирает конфигурацию запуска.
- `imports.ts` разбирает и разрешает статические runtime imports.
- `preloads.ts` читает параметры подготовки среды из конфигурации пакета.
- `jsx-runtime.ts` определяет JSX transport из exports владельца preload.
- `trace.ts` запускает процесс, принимает записи и возвращает результат.
- `trace-preload.ts` подключает части сборщика в дочернем Bun.
- `instrument.ts` добавляет контекст в callback bodies через TypeScript AST.
- `context.ts` хранит варианты групп и асинхронный контекст тестов.
- `observe.ts` записывает вызовы, аргументы и порядок завершения.
- `serialize.ts` переносит значения без вызова getters.
- `call-location.ts` находит внешний frame вызова.
- `pending.ts` ожидает завершения отправок до итогового IPC report.

## Данные и проверки

В `spec/scenario.spec.ts` два варианта: серверный readPackage и DiagramNode
из соседнего WebXR checkout с настоящим рендером. Оба вызывают readScenario
только с путём. Каждый проверяет данные и сохраняет полный результат через
штатный `toMatchSnapshot`. Из stderr удаляются только измерения длительности Bun.
Изображения отдельно в файлы не записываются.

В `test` проверяются внутренние механизмы, включая параллельные вызовы,
сериализацию и определение среды. Сериализация читает собственные enumerable
properties; функции, promises, ошибки и циклы получают явные метки.

Контекст распознаёт прямые имена describe/test, block-bodied callbacks и each
с подстановками $field. Переименованные registrars, printf placeholders,
concise callbacks и контекст hooks пока не поддержаны. Вложенный test сохраняет
группу своего варианта после await. Вызов непосредственно в describe после
await пока может не иметь группы; такие записи нельзя считать полным покрытием.

## Подготовка данных и тело теста

Сценарий импортирует и вызывает проверяемую функцию обычным способом.
Для чтения через readScenario ручные mock и spyOn не требуются.
Параметризация describe.each задаёт варианты, а test.each применяется к
действительно параметризованным проверкам данных.

Общие неизменяемые данные, не зависящие от варианта или отдельного запуска теста,
определяются на уровне модуля. Например, путь к общей директории фикстур
вычисляется один раз вне тела теста.

Данные вариантов задаются параметризацией групп и тестов. Тело теста вызывает
проверяемую функцию с данными сценария и проверяет полученный результат.
Ресурсы, требующие отдельного создания и очистки для каждого теста, сохраняют
свой жизненный цикл и не становятся общим изменяемым состоянием модуля.

## Предстоящая проверка

Каждый пропуск теста или группы сопровождается TSDoc с `@remarks`
непосредственно перед объявлением. Заметка объясняет условие пропуска
и причину, по которой проверка не выполняется в этом случае.
Это относится и к условным пропускам, и к постоянно отключённым тестам.
Наличие непустого `@remarks` проверяется в [спецификации пропусков](../spec/skip.spec.ts).
Смысл пояснения пока оценивается при чтении: тест проверяет наличие заметки.

В спецификации сценариев нужно проверять структуру самого теста:
общая подготовка неизменяемых данных не должна повторяться внутри его тела.
Эта проверка пока не реализована.
