# Как собираются пакет и общая оболочка

Реализация: [сборка пакета](../package-build.ts), [общая оболочка](../shared-browser-build.ts) и [планировщик](../build-scheduler.ts).

Связанные условия: [идентичность модулей](modules.md), [кэш](cache.md), [оценка нагрузки](preflight.md), [ревизии пакета](../../sessions/notes/revisions.md).

## Очередь, компиляция и отмена

Техническое исполнение принадлежит [BuildQueue](../../tech/build/queue/index.ts):
FIFO, slots, отмена ожидания, terminal transitions и наблюдение worker.
[Сборочный координатор](../build-scheduler.ts) проверяет предметные package/shared
данные и проецирует прежний контракт status и событий. Очередь не выбирает пакет,
исходники или рабочую ревизию. Ошибка наблюдателя не меняет исход операции.
[Ожидание процесса](../../tech/process/wait/index.ts) подтверждает завершение
точного worker и его группы; [снимок процессов](../../tech/process/sample/index.ts)
и [измерение дерева](../../tech/process/measure/index.ts) не управляют процессами.

Каждый package имеет собственную serial queue. Общий scheduler по умолчанию
допускает одну тяжёлую работу на поддерживаемом Intel host; явно заданный предел
остаётся ограниченным. Package и shared-browser workers используют одни slots.
Зависшая работа завершается по своему бюджету, после чего очередь продолжает работу.
Compile/protocol/activation имеют timeouts; detach/reconfigure отменяют exact
candidate. Worker создаётся в собственной process group: завершение подтверждается
для него и его потомков, без поиска и остановки процессов по имени команды.
Кратковременный EPERM при проверке завершающейся группы не подменяет исходную
отмену: signal 0 повторяется в ограниченном окне до подтверждённого исчезновения.
Постоянный отказ доступа остаётся ошибкой, а не признаком успешного завершения.
Package compile получает отдельный bounded budget 120 секунд: это покрывает
fresh Template/TypeScript initialization на поддерживаемом Intel host, но не
ослабляет per-candidate cancellation или exact child termination. Общая сборка
платформы и host выполняет два native прохода для immutable namespace и имеет
отдельный бюджет 240 секунд. Обычный HTTP idle timeout равен 125 секундам;
запросы подготовки отключают его штатным Bun Server.timeout(request, 0), поскольку
ожидание общей очереди не является зависшим worker. Компиляция по-прежнему
ограничена своим бюджетом, а отмена HTTP закрывает только конкретное ожидание.
Ограничение ожидания MCP не считается автоматически падением compiler. Ответ
CheckWaitTimeout содержит актуальные packages, очередь и operationIds продолжающейся
работы; агент читает status/wait вместо создания второй сборки. Старый failed
не объявляется результатом нового check: новая ошибка сопоставляется с baseline
generation/failedRevision, а неизвестный результат всей проверки помечается явно.

Cold package build выполняет один browser Bun.build. Прямые exports и фактические
зависимости проверяются до публикации; повторный отдельный exports bundle не
создаётся.
Общая оболочка хранит собственный receipt по тому же fingerprint plan; cache hit
проверяет входы и digest выходных файлов и не вызывает Bun.build.
CSS общей оболочки хранится в тех же immutable shared assets. GET landing/fallback
не запускает сборку выбранного пакета или self-documentation только ради страницы
и её стилей. Страницы читают готовую оболочку. Подготовка пакета по check или первому
переходу использует её проверенный кэш; при необходимости готовит новую.
Ошибка shared-сборки доступна в read-only status.
Multi-package isolation, которая поднимает несколько compiler/server children и
регистрирует Bun plugins, выполняется отдельным test process и не делит
process-global plugin state с unit и server integration suite.

## Подготовка после проверки

Изменения файлов сами не запускают discovery, тесты или компиляцию. Сервер
сохраняет каталог и готовые ревизии. Навигация использует доступную сборку;
пакет без неё проходит подготовку при выборе пользователем. Подписка читает
состояние и не запрашивает компиляцию.

Полная команда разработки `bun run check` заканчивается сборкой только после
успешных предшествующих проверок. `storybook_check` перечитывает каталог,
проверяет актуальность входов, готовит общую оболочку и выбранные пакеты.
Исполняемые сценарии проверяются до browser bundle; провал проверки сохраняет
рабочую ревизию. Неизменившиеся входы повторно используют проверенные артефакты.

`check(live:false)` подготавливает кандидата. После проверки его представления
`check(live:true)` применяет ревизию через HMR. Первое открытие без рабочей ревизии подтверждает кандидата через ту же
независимую browser inspection. Preview и подписка сами его не применяют. Полнота исходников сверяется на границах операции;
изменение входных файлов во время сборки отклоняет её результат.

## Переходный и строгий пакеты

Внутри подготовки кандидата исполняется [нормативный сценарий Package](../../archetypes/package/spec/scenario.spec.ts)
через тот же readScenario, который раскрывает документацию и MCP. Общие
требования, применимость Repo/Domain/Component и однозначность их границ
выражены в самом сценарии. Сборщик не содержит реестра классов и не разбирает
названия отдельных test. Полный исходный ReadScenarioOutput сохраняется
в verification.json той же ревизии; второе предметное представление не создаётся.

Переходный пакет сохраняет нарушения стандарта в warnings. Неподдержанный
авторский preview обозначается предупреждением и отсутствует в готовых
представлениях. Строгий пакет требует полного прохождения всех применимых
обязательных проверок. TODO, not-executed, необъяснённые пропуски и отсутствие
выполненных проверок не подтверждают завершение. Собственные сценарии пакета
выполняются существующей подготовкой preview один раз; падение поведения,
компиляции, линковки, timeout и отмена остаются отказами обоих режимов.

Нормативные исходники и исходники пакета входят в отпечаток той же ревизии.
Status, discovery и открытие доступной ревизии проверку не запускают. Нормативный
сценарий и компиляция занимают один общий slot последовательно. Документированный
неприменимый раздел сценария не становится отдельной ошибкой пакета.

Сводка verification содержит только исход и сообщения; первичными данными
остаются test/expect выполненного сценария. MCP и browser используют те же
предупреждения. Строгий режим закрепляет [применение ревизии](../../sessions/notes/revisions.md).
