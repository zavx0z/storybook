# Адресные беседы

Предмет определяется каноническим адресом внутри Project. У одного предмета
могут работать несколько именованных исполнителей с независимыми беседами,
настройками подключения, provider session и очередями входящих задач.
Строковый адрес выбирает прежнюю default-беседу; `{address, executorId}` выбирает
ровно уже известного исполнителя этого предмета. Неизвестный UUID не создаёт
новую беседу. `create({address, label})` явно создаёт именованного исполнителя,
`list(address)` перечисляет только сохранённые и уже загруженные беседы этого
адреса. Имя исполнителя `executorLabel` отделено от имени предмета `label`.

UUID исполнителя отличается от id беседы, адреса и native sessionId провайдера.
Именованные исполнители получают новый UUID при create. Default и прежняя
история без executorId получают устойчивый UUIDv5 от chat id; поэтому read/list
с последующим restart сохраняют точный выбор ещё до первого prompt/prepare.
Пустое чтение не создаёт файл. При переносе все три identity сохраняются.
Корень `/` обозначает Project, остальные адреса разрешаются по действующему каталогу.
Выбор представления, секции Inspector, варианта сценария и ревизии не создаёт
новую беседу. Чат расположен первой секцией Inspector и доступен также на
страницах Repo и директорий.

История хранится в `meta/chat` физического владельца, независимо от cache
Storybook и сборочных артефактов. Для корневой беседы владельцем является Project.
Прежний default-файл `<hash(address)>.json`, его chat id и native sessionId
сохраняются. Дополнительные беседы имеют файлы `<hash(address)>.<executorId>.json`
в `meta/chat` того же владельца. Create сохраняет пустую именованную историю;
default-файл появляется при первом сообщении или явном подключении для настроек. Формат `schemaVersion: 2` содержит единственную
каноническую timeline: сообщения со штатными ACP ContentBlock, supplied context,
вызовы инструментов с накопленным состоянием и исходными updates, переданные
рассуждения, другие полученные события ACP и итог turn. Текстовые `messages`
являются вычисляемой проекцией для прежних потребителей и в JSON не дублируются.
Общий browser-safe reader [Chat History](../../history/index.ts) проверяет timeline
по своему контракту и опубликованной JSON schema ACP.
История содержит сведения, необходимые для восстановления ACP-сессии. Секрет
назначения окружения хранится только в памяти сервера и не передаётся модели.
Черновик хранится отдельно по identity беседы в локальном состоянии браузера.

При переходе прежний общий `chats` Project служит источником существующих историй.
При запуске известные адреса копируются в `meta/chat` владельцев без запуска агентов;
первое чтение также подхватывает ещё не перенесённую историю. Сообщения, id и
sessionId сохраняются. Уже существующая история назначения не перезаписывается.
Старые файлы остаются для восстановления, а неразрешённые адреса требуют явного
соответствия владельцу. Новые записи выполняются только в хранилище владельца.
Сообщения формата 1 переводятся в timeline с прежними id, порядком, текстом,
sessionId, cwd и usage. Исходный файл сохраняется в `.schema1` перед последующей
записью новой версии; прежний общий каталог также остаётся для восстановления.
Миграция не заявляет полноту старой текстовой истории.

При физическом переносе владельца новый адрес сам по себе не открывает файл
прежнего адреса. Владелец приложения передаёт [StorybookChatSession](../../session/index.ts)
точное соответствие прежних и текущих адреса и cwd; текущий адрес проверяется
каталогом. Перенос касается только этой беседы, создаёт новый файл атомарно без
перезаписи другой истории и сохраняет прежний файл для восстановления. Id,
сообщения и ACP sessionId сохраняются, поэтому браузерный ключ черновика
остаётся прежним. Повтор операции не стирает новые сообщения. Активный turn выбранного исполнителя
нужно завершить до переноса; пустое чтение не создаёт файл и не запускает агента.
Для именованной беседы relocate передаётся executorId; без него переносится
прежняя default-беседа. Остальные исполнители того же адреса остаются на месте.
После проверки назначения и завершения работы окружение источника освобождается.
Устойчивое намерение `<source file>.relocated` записывается ДО создания destination.
Исходный JSON остаётся неизменным для восстановления и исключается из активных
read/list, даже если старый предмет продолжает существовать. При ошибке copy
source остаётся закрытым; повтор того же mapping завершает перенос. Другой mapping
не переписывает intent. Старый mapping не активирует destination, уже перенесённый
дальше. Если перенесён default, строковый выбор старого адреса сообщает перенос,
а не создаёт другого исполнителя неявно.
Следующее сообщение пробует штатное восстановление ACP в новом cwd. Ошибка
восстановления остаётся видимой ошибкой беседы и не начинает новый разговор.

Настройки модели и уровня мышления загружаются при явном открытии выбора через
ACP `configOptions`. Подготовка создаёт или восстанавливает сессию, но не вызывает
`session/prompt`. Выбор применяется через `session/set_config_option`; список
допустимых уровней после смены модели возвращает агент. Во время ответа настройки
не меняются. Начальные значения определяет адаптер, а выбранные — его сессия;
глобальный конфиг Codex не переписывается.

Контекст показывается по `usage_update.used` и `usage_update.size`, включая
подтверждённые данные восстановления. Последние значения сохраняются с беседой.
До получения данных индикатор показывает их отсутствие, а не выдуманный ноль.
При смене модели старый лимит не выдаётся за лимит новой модели.

Composer использует многострочный textarea: Enter отправляет сообщение,
Shift+Enter оставляет новую строку, подтверждение IME не отправляет текст.
Одна круглая кнопка переключается между отправкой и остановкой. Сообщения
пользователя имеют отдельный фон; Markdown и код используют существующий
компонент отображения с подсветкой.

Создание представления и чтение пустой истории не запускают модель. Read/list
могут запустить ранее сохранённые и ещё не начатые входящие задачи после restart;
это восстановление принятой работы, а не генерация ради просмотра. Первое сообщение открывает
подключение к Codex через готовый ACP-адаптер. Следующие сообщения используют ту же сессию. При полной локальной истории
и объявленной провайдером `sessionCapabilities.resume` подключение использует
штатный `session/resume`. Для неполной или мигрированной истории и адаптеров
без этой возможности используется `session/load`; replay отделяется от live.
Messages объединяются строго по provider messageId, вызовы — по toolCallId.
Replay сообщения заменяет его неполное локальное содержимое. Все реально
полученные chunks и updates остаются свидетельствами: replay-загрузки различаются
batchId, отдельные события получают собственные id и sequence. ToolCallId
объединяет одну строку инструмента и не подменяет identity отдельных updates.
Replay без messageId не сопоставляется по тексту: отдельная запись имеет
`origin: replay` и diagnostic о неустановленной identity. Поэтому нельзя обещать
полное устранение аварийных потерь или восстановление raw provider context.
Внутренние данные модели, которые адаптер не передал, не достраиваются. Восстановление сохранённой сессии не подменяется новым разговором;
ошибка восстановления показывается пользователю. Повтор HTTP-отправки с тем же
идентификатором не создаёт второе исполнение сообщения.

Одновременно у одного исполнителя выполняется один turn. Разные исполнители,
включая участников одного адреса, независимы.
Переход страницы и отключение потока состояния снимают подписку, сохраняя работу.
Остановка относится к выбранной беседе; запросы разрешений отображаются
в её Inspector и получают только явно выбранный пользователем ответ.
После прерывания процесса незавершённое сообщение автоматически не повторяется.

Приложение назначает сохраняемому executorId отдельное окружение предмета до
подключения ACP. Общий `/api/environment` возвращает стартовый контекст через GET
и исполняет полную команду `{name, arguments}` через POST. Ключ привязан к
назначению; модель его не получает. Внешний управляющий клиент использует тот же
вход с областью Project и может читать представление внутреннего исполнителя.
`knowledge.read` начинает с назначенного предмета и раскрывает подробности по
переходам children. Чтение общих правил не расширяет файловую область инструментов.

Первая задача в provider session передаётся после содержимого окружения в одном
prompt. Контекст сохраняется отдельной записью истории; повторный turn и resume
той же сессии не загружают неизменный контекст снова. При изменении окружения или
provider session контекст передаётся заново. Открытие настроек не запускает prompt.
Полное текстовое сообщение с JSON-командой исполняет окружение, после чего сессия
доставляет его ответ модели и продолжает работу. Примеры в Markdown, смешанный текст
и мультимедиа не интерпретируются как команды. Ошибка транспорта или прерывание
никогда не повторяют потенциальную мутацию автоматически. Команда, фактические
события инструмента и переданный результат остаются в сохраняемой истории.

Внутреннее ACP-подключение получает пустой список MCP; прежние HTTP-обёртки
предметного MCP пока доставляют обращения тому же исполнителю окружения.
Собственные инструменты Codex требуют отдельного ограничения у провайдера:
отсутствие MCP и назначенный `cwd` не устанавливают изоляцию native filesystem.
Для внутреннего Codex применяются штатный read-only режим, отключение shell,
unified exec, web search, view image, multi-agent и hooks; автоматические проектные
инструкции и блок skill instructions отключены только в этом дочернем процессе.
Модель и уровень мышления этим не фиксируются. Эти настройки уменьшают параллельные
пути исполнения, но до живой проверки не объявляются полным no-tools контрактом.
Отдельного репозитория ACP и собственной реализации протокола здесь нет.
Перенос беседы закрывает прежнее назначение и создаёт новое в новой области;
обычное переподключение ACP сохраняет назначение.

Снимки беседы передаются по авторизованному WebSocket `/api/events`: browser
registry grant разрешает подписку `chat:<канонический адрес>`, ответ
`chat.snapshot` содержит адрес и снимок. Первое состояние передаётся сразу,
последующие изменения объединяются за 50 мс. Закрытие сокета снимает подписку,
не отменяя выполнение беседы. Переподключение получает новый grant и свежий
снимок, сохраняя черновик и не повторяя prompt.

Постоянный HTTP-поток для каждой вкладки не используется: такие запросы
занимали соединения общего HTTP/1.1-пула браузера и могли задерживать загрузку
настроек и обновлений. Старый `/api/browser/chat/events` возвращает конечный
ответ 410, чтобы старые вкладки освобождали соединения и могли загрузить оболочку.

ACP prompt принимает текст либо штатные ContentBlock. В Snapshot раскрываются
реальные capabilities агента; image, audio и embedded context передаются только
при явно объявленной соответствующей input capability. Отсутствие поддержки
audio не заменяется предположением о возможности адаптера. Полученные media
сохраняются независимо от того, умеет ли текущий UI показывать их содержимое.
Новые и уже сохранённые записи не обрезаются по произвольному лимиту истории.
Текст входного сообщения сохраняет действующий лимит 64000 символов.

Входящая задача сохраняется через `enqueue(target, content, requestId)` даже при
занятом получателе. Сообщение содержится один раз в canonical timeline; `pending`
содержит только его id. Повтор requestId с тем же content не создаёт второго
сообщения или исполнения; другой content для того же requestId отклоняется.
Очередь исполняется последовательно после текущей работы. Prompt сохраняет
прежний отказ при занятости; enqueue используется для адресной доставки команде.

Начало отмечается устойчивым turn started и удалением id из pending непосредственно
перед первым provider attempt. После сбоя такая задача автоматически не повторяется:
сохранённое начало не доказывает успешную доставку или завершение. Остальные pending
восстанавливаются при загрузке исполнителя. Отказ подготовки подключения до start
оставляет задачу pending; очередь останавливается до явной подготовки либо restart,
сохраняя последующие входящие задачи. Остановка сервера сохраняет ещё не начатые
задачи. Отмена человеком касается текущего turn; другие pending остаются в очереди.
Это не гарантия exactly-once для внешних эффектов: неопределённый результат уже
начатой операции сохраняется в истории и требует отдельного решения.
