# Дисковая история: ограниченность серверного состояния

Измерение выполнено 2026-10-05 на текущем Intel Mac, Bun 1.4.2
(`744846f84`). Использован временный каталог `chat-disk-archive-*` системного
`tmpdir`; рабочие и архивные истории пользователя не читались и не менялись.

Источник проверки — [archive.test.ts](../../../test/archive.test.ts), тест
«10000/100000 дисковых записей оставляют bounded residency и страницы,
холодный lookup работает после rebuild». Команда:

```sh
CHAT_ARCHIVE_BENCHMARK=1 bun test ./chat/session/test/archive.test.ts --test-name-pattern '10000/100000'
```

Созданы 100000 разных canonical user entries с последовательностями
1–100000. Запись выполнялась 100 транзакциями по 1000 entries. Между
транзакциями не сохранялся полный массив истории. Проверки на 10000 и
100000 entries наблюдали страницу из 32 заголовков и отсутствие resident
entries у handle. После записи SQLite connection закрыт, файл индекса
удалён; повторное открытие восстановило индекс из подтверждённого текстового
журнала и выполнило lookup первой и последней записей.

| Наблюдение | Значение |
|---|---:|
| Запись и flush 100000 entries | 7033.147 ms |
| Streaming rebuild после удаления SQLite | 3539.809 ms |
| JS heap после GC перед записью | 5805838 bytes |
| JS heap после GC после записи | 8463666 bytes |
| Разница после GC | 2657828 bytes |
| Наибольший heap из выборок после каждой транзакции | 15108284 bytes |
| Подтверждённый NDJSON журнал | 15794775 bytes |
| Восстанавливаемый SQLite индекс | 36384768 bytes |
| JSON последней страницы из 32 заголовков | 4868 bytes |
| Resident entries после rebuild | 0 |
| Открытые SQLite connections после rebuild | 1 |

Выборочный максимум heap не является непрерывно измеренным пиком. Это
`process.memoryUsage().heapUsed`, а не RSS процесса или native SQLite память.
Время включает реальные обращения к ФС и синхронизацию подтверждённых
транзакций. Страницы проверены с холодным rebuilt индексом; это не измерение
UI, GPU, provider replay или визуальная приёмка.

В этом прогоне тест завершился за 10598.69 ms; общий запуск Bun — 11.67 s,
1 pass, 0 fail, 17 assertions. Полный предшествующий прогон архивных проверок:
8 pass, 0 fail, 60 assertions, 13.09 s.

## Проверяемые пределы

Общий pool содержит не больше 8 SQLite connections, каждый использует
`cache_size=-2048` и `temp_store=FILE`. Handle хранит metadata и счётчики,
не полный список entries. Очередь ограничена 128 вызовами и 32 MiB
сериализованных входов; вызывающий обязан ожидать Promise записи. В тесте
1000-entry batches максимум queued bytes проверен как меньше 1 MiB.

Обычная страница содержит 32 заголовка, допускает не больше 64 и 64 KiB
заголовков. SQL извлекает малую preview, не body или raw payload.
Body читается отдельно с пределом 16 MiB. Evidence имеет отдельный диапазон
до 64 событий и стандартный byte budget 128 KiB; один большой event может
быть прочитан отдельной страницей до 16 MiB. Превышение body/event reading
limit возвращает явную ошибку; исходные данные остаются в журнале.

Сами текстовые истории не удаляются по возрасту или количеству entries.
SQLite является cache: удаление проверенно восстанавливает адресацию,
не удаляет единственный источник опыта. Corrupt committed journal не
заменяется пустой историей; truncation или hash mismatch дают ошибку.

## Одиночные updates после роста истории

Дополнительный прогон выполнен после удаления `COUNT(*)` из каждой записи
и добавления индексов started/terminal request, assistant sequence и parent
identity. Предыдущее измерение размера SQLite относится к предыдущему набору
индексов; текущая серия не перемеряла размер файла cache.

```sh
CHAT_ARCHIVE_BENCHMARK=1 bun test ./chat/session/test/archive.test.ts --test-name-pattern '1000 одиночных updates'
```

Обе временные истории сначала сохраняют один tool и три turn markers;
далее добавляются соответственно 1000 и 100000 user entries. Затем один
и тот же холодный tool получает 1000 **отдельно подтверждённых** updates,
после которых выполняются 100 отдельных metadata commits. Запись журнала,
синхронизация ФС, атомарное переключение header, stale-writer check и
обновление SQLite входят в измеренное время.

| Операция | 1000 user entries | 100000 user entries |
|---|---:|---:|
| 1000 одиночных updates | 3559.872 ms | 3455.743 ms |
| Среднее одного update | 3.560 ms | 3.456 ms |
| 100 metadata commits | 272.046 ms | 213.013 ms |
| 1000 циклов request/assistant lookups вместе с assertions | 86.814 ms | 96.875 ms |

Рост истории в 100 раз в этом прогоне не увеличил время одиночных updates.
Разница малых времён включает шум ФС и исполнения; это ограниченный
benchmark конкретной формы обновления, а не универсальная оценка latency.

Тест дополнительно проверяет реальный `EXPLAIN QUERY PLAN`: hasStarted,
последний started, отсутствие terminal и отсутствие assistant после границы
используют `started_request`, `started_turn`, `terminal_request` и
`assistant_entry`; полного `SCAN entry` в этих планах нет. Runtime использует
`activeRequest` из metadata; request lookups нужны при миграции legacy.
Total теперь изменяется на фактическую разницу append/create/remove в
предварительной транзакции. Полный `COUNT(*)` выполняется только при rebuild.

Прогон: 1 pass, 0 fail, 8022 assertions; тест 16169.43 ms, общий запуск
17.34 s. Отдельно проверены конкурирующие writers одного файла: одна запись
принимается, stale writer получает явный отказ, reopening/retry сохраняют
оба сообщения без затирания ранее принятого. Writer leases освобождаются
при завершении; pool остаётся ограничен восемью connections.
