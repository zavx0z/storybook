# Где размещать компонент и его реализацию

## Определение

Самостоятельный Component предоставляет одну конкретную возможность через
основную реализацию и её публичный протокол. Его код, контракты, сценарии
и частные помощники принадлежат собственному пакету. Граница определена
[единым стандартом](./architecture.md#определение).

## Вход компонента и его внутренние части

Основная реализация находится в корневом `index.ts` либо
`index.tsx`. Вход предоставляет одну основную реализацию через default и именованные
типы её контракта. Дополнительные самостоятельные компоненты получают свои
пакеты. Подмена реализации реэкспортным фасадом не допускается.
[Публичные входы и экспорт контрактных типов](../../package/meta/notes/draft-exports.md).

Отдельные вспомогательные функции и частные компоненты отображения верхнего
уровня выносятся в `src/` своего пакета. Небольшой размер не является основанием
оставлять несколько таких объявлений во входе. Локальные обработчики и callbacks
внутри основной реализации остаются её частью. Связанные помощники могут
находиться в одном частном файле; одного экспорта на каждый файл `src` не требуется.
Если выносить нечего, `src/` не создаётся.

Самостоятельная общая часть нескольких пакетов получает собственного владельца
и используется через его публичный API. Соседние пакеты не импортируют чужие
`src/`. Частный общий код внутри одного пакета остаётся его
реализацией и не создаёт отдельный структурный класс.

Типовые роли и определения публичной формы находятся в `contract/`,
а нужные только реализации типы — у использующего кода.
Точка namespace, размещение определений и публикация типов следуют
[правилам Contracts](../../contracts/meta/notes/draft-contracts.md).
Наличие частных helpers не определяет доступность документации или сценария.

## Форма основной реализации

Default может быть функцией, классом, таблицей или символом с самостоятельным
назначением. Фиктивная callable-обёртка не добавляется. Имя функции/класса либо
константы сохраняет смысл в исходнике и помогает диагностике; публичное имя
при реэкспорте назначается независимо. Минификация не обязана сохранять диагностическое имя.

Для значения с выводимым TypeScript типом пустой output.ts не требуется.
Самостоятельное соглашение об обмене данными получает публичный контракт;
реальная полнота этого соглашения проверяется поведением, а не наличием файла.
Незавершённость таких проверок остаётся [явной](../meta/notes/verification.md).

## Составность и принадлежность

[Container](../../container/src/architecture.md) композирует принадлежащие компоненты
и вложенные контейнеры с компонентами в одно целое. Его публичный API имеет ту же
форму, что у Component: собственная реализация через default и именованные типы
собственного контракта. Собственная публичная runtime-реализация вместе с
принадлежащими вложенными пакетами задаёт структурного кандидата Container;
фактическую композицию раскрывают runtime-ссылки и сценарии поведения.

Component может участвовать в средовой реализации
[Domain](../../domain/src/architecture.md) или в группе
[Cluster](../../cluster/src/architecture.md). В Cluster он сохраняет собственный
протокол, соблюдает общий протокол группы и может расширять его особенностями.
Component без принадлежащих вложенных частей может использовать другие пакеты:
прямой импорт зависимости не переносит её к новому владельцу.

## Документация и представления

Корневой TSDoc описывает компонент, а `spec` раскрывает его использование.
Варианты одного компонента сохраняют владельца и не создают новые пакеты.
Открытый вопрос preset-представлений описан
[у владельца представлений](../meta/notes/presentation-ownership.md).

Текущий Storybook ещё показывает обычные директории переходных пакетов.
Его признаки остановки обхода по `index.tsx` и `src/` не определяют новый класс
Component. Подробности действующего обхода, выбора TSDoc и маршрутов собраны
[в описании проекции файлов](../../package/meta/notes/draft-projections.md).
