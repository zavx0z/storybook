# Модель контрактов

Контракт — принадлежащая предмету форма данных и отношений между владельцами.
Он выражает типовую часть публичного протокола: вход, результат и слоты
реализации, когда соответствующие роли нужны. Контракт не исполняет возможность
и не доказывает, что заявленная связь состоялась.

## Владение общим и собственным протоколом

Component владеет протоколом своей возможности, Container — протоколом
исполняемого целого. Cluster владеет общим протоколом смысловой группы.
Каждый ребёнок сохраняет собственный протокол, который соответствует общему
и может расширять его своими особенностями. Расширение сохраняет происхождение
общих определений и не превращает их в копии ребёнка.

У Domain каждому средовому входу соответствует одна основная реализация
и её протокол. Принадлежность протокола домену либо выбранной реализации,
размещение общих и средовых частей и форма публикации общего протокола Cluster
остаются [открытыми решениями](../../package/notes/archetype-transition.md#открытые-решения).
Существующее namespace-представление не считается автоматически достаточным
для этих отношений.

## Действующая форма Component и Container

Component и Container публикуют ровно два корневых вида API: собственную
runtime-реализацию через `default` и собственное пространство типов через
именованный type-only экспорт. Имя namespace образуется из полного имени пакета
со scope в PascalCase: `@zavx0z/storybook-app` → `Zavx0zStorybookApp`, `@zavx0z/storybook-app-web-release` → `Zavx0zStorybookAppWebRelease`,
`@zavx0z/storybook-contracts` → `Zavx0zStorybookContracts`. В `contract/index.ts`
пространство непосредственно объявляет формы `Input`, `Output` и `Slots`,
когда соответствующие роли нужны. Их состав собирается здесь, без отдельных
одноимённых определений и промежуточных aliases для публикации. JSX может использоваться как
Component, так и Container; типовые слоты не обязательны для каждого пакета.

Несовпадение имени namespace с полным именем его пакета возвращается как
предупреждение `namespace-name`, с фактическим и ожидаемым именами.
Чтение контракта продолжается; имя исходного владельца сохраняется и при реэкспорте.

Все собственные типы, образующие эти публичные формы, принадлежат `contract/`.
Тип, нужный только реализации, остаётся у использующего его кода. Файлы внутри
`contract/` свободно группируют типы по смыслу: имена `input.ts`, `output.ts` и
`slots.ts` не обязательны, как и правило об одной декларации на файл.
Отдельные файлы содержат составляющие контракта с предметными именами;
целая форма роли не выносится туда только ради alias в namespace.
Типовые зависимости подключаются обычными `import type` в начале модуля.
Форма роли может выводиться из чужого контракта, например `type Input = Zavx0zStorybookAppWebRelease.Output`.
Короткие имена описывают тип внутри своего пространства. Старайтесь обходиться
без повторяющих контекст префиксов вроде `ContractInput` или `ComponentOutput`.
Пакет не вводит `types`-переопределение `package.json` для своего исходного API:
публичное пространство публикуется обычным корневым экспортом.

Файлы одной реализации могут напрямую импортировать типы друг друга. Между
пакетами потребитель обращается через публичное пространство исходного владельца:
`import type {Zavx0zStorybookAppWebRelease} from "@zavx0z/storybook-app-web-release"`, затем `Zavx0zStorybookAppWebRelease.Output`.
Реэкспорт такого пространства сохраняет происхождение его деклараций;
само опубликование чужого namespace не создаёт собственный контракт.
Это не отменяет принадлежащего Cluster общего протокола.
Для действительно связанной
формы используйте `Pick`, `Omit`, indexed access и другие штатные операции типов.
Связь может относиться и к примитиву; само отличие от структурного объекта не
отменяет реальную зависимость. Повторяйте поля только если это отдельный смысловой
контракт, а не копия формы другого владельца.

## Текущие проверяемые варианты

Нормативный сценарий `@zavx0z/storybook-contracts` проверяет четыре положительных
варианта и прежнюю отрицательную применимость Domain-фасада.
Эта последняя проверка требует пересмотра по новым определениям Domain и Cluster.
Роли пакета и JSX независимы: Container, как и Component, может иметь
обычный или JSX-вход.

* Component в обычном варианте описывает принадлежащий ему вход и результат,
  когда они составляют публичную форму поведения. Для Promise результат означает
  значение после `await`; выводимый тип сам по себе не требует повторной декларации.
* JSX Component может иметь `Input`/props и `Slots`. Сам факт JSX-результата не
  требует `Output`. Сохраняется текущая структурная семантика
  `JSX.Element<Slots>`; номинальная иерархия идентичности не добавляется.
* Container владеет контрактом целого; его части сохраняют собственные
  пространства. В обычном варианте сценарий проверяет ту же принадлежность для
  не-JSX входа.
* JSX Container владеет контрактом JSX-целого. Слоты и прочие типы частей
  остаются у своих владельцев; вложенная композиция не переносит их родителю.
* Прежний Domain-фасад в текущих примерах публикует пространства владельцев
  через реэкспорт. Проверка сохраняет полезное свидетельство происхождения,
  но её запрет собственного пространства нельзя применять к общему протоколу
  Cluster или считать проверкой средовых протоколов нового Domain.
  Type-only экспорт не доказывает runtime-передачу данных.

`@zavx0z/storybook-contracts` предоставляет default-читатель `readContract` и типы
своего API под пространством `Zavx0zStorybookContracts`. Читатель раскрывает native символы
TypeScript и происхождение типов без исполнения проверяемого пакета. Сценарий
пока проверяет перечисленные выше варианты. Читатель ещё не подключён
к Storybook discovery, UI или MCP; обновление заметки не меняет эту интеграцию.

## Документация форм

Сценарий Contracts вызывает [сценарий TypeDoc](../../typedoc/spec/scenario.spec.ts)
с путями собственных исходников контракта. Правила тегов и размещения описаний
принадлежат TypeDoc и не копируются в Contracts. Дочерние `todo` сохраняют
непроверенность смысла; успешный разбор комментария не подтверждает его полноту.

## Границы ответственности

Contracts отвечает за общую модель владения и формы данных, чтение контрактов
и сценарии её применимости. Package продолжает отвечать за package identity,
exports, зависимости и структурную классификацию. Discovery отвечает за
обнаружение физических файлов, безопасное чтение и целостность источника.
Component и Container сохраняют исполнение, композицию и проверки фактического
поведения. Domain отвечает за общие правила сущности и её средовые входы;
Cluster — за общий протокол группы и организацию доступа к самостоятельным участникам.

UI и адреса существующего просмотра зафиксированы отдельно в
[заметке о представлении](./presentation.md). Discovery, UI и MCP сохраняют свои
текущие источники и интеграции; этот владелец их не меняет.
