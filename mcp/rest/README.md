# Storybook REST

Пакет предоставляет обработчик единой точки входа HTTP API. Основной сервер
Storybook подключает его после проверки авторизации.

Пустой запрос возвращает подключённые канонические корни, например `storybook`
и `webxr`. Каждый дочерний раздел содержит только node для следующего запроса
и description. Общий `@storybook/route` разрешает адрес и непосредственных
детей по зарегистрированным корням, workspace и видимым директориям. Поэтому
`storybook/archetypes` и `webxr/nodes/node/diagram` принадлежат одному дереву,
а технические директории и старые короткие адреса не становятся маршрутами.
REST не хранит отдельный каталог и не повторяет правила структурного разрешения.
Успешный обзор не содержит служебных status и schemaVersion.

Обзор владельца возвращает доступные file-backed представления в `views`.
Представление `scenarios` у владельца с непосредственным `spec/scenario.spec.ts`
либо `.tsx` возвращает JSON-документацию: node, title, content и вложенные
sections. Адрес node остаётся адресом владельца: `webxr/nodes/node/diagram`
или `storybook/archetypes/specs/scenarios`; представление выбирается через input.
Абзацы text/value связывают авторское пояснение с предметными данными или примером.
Варианты, темы и пункты используют одну форму раздела с сохранением исходного
порядка. Пустые структурные списки отсутствуют; реальные пустые значения сохраняются.
Неподтверждённые положения, неприменимость и ошибки обозначаются в notes.
Два сценарных файла одного владельца считаются неоднозначностью.

Query адреса либо input выбирают представление и вариант; они не могут задавать
разные значения. Цепочка заголовков тем остаётся в input. Выбранная тема
возвращается целиком с родителями, без соседних ветвей. action=data с выбранным
представлением возвращает поле scenarios
с исходными условиями и состояниями. Документ не изменяет полный результат
инспектора. Точный формат принадлежит [описанию JSON-документации](scenarios/notes/presentation.md).

Подключающий сервер может передать результат `readSpec` применённой ревизии,
чтобы переключение раздела не запускало тест повторно. Если подготовленного
результата нет, чтение сценария выполняется через публичный `readSpec({path})`.
Произвольные пути через input пока не поддержаны. Диагностический запрос
`{"action":"journal"}` возвращает только серверную сводку доставки записей;
он не запускает сценарии и не требует работающей вкладки.

MCP передаёт запрос серверу и возвращает его ответ. Логика обзора принадлежит
этому пакету и исполняется в HTTP-сервере. [Сценарии](scenarios/README.md) и
[чтение спецификации пакета](package/index.ts) также принадлежат этой стороне.
Независимость транспорта закреплена в [сценарии прокси](../proxy/spec/scenario.spec.ts)
и [сценарии MCP-адаптера](../server/spec/scenario.spec.ts).

Журнал MCP хранит последние 20 запросов: имя инструмента, параметры, время,
статус и полный публичный ответ без обрезки по длине. Окно журнала показывает
одну выбранную команду. Ответ целиком отображается в CodeEditor с подсветкой JSON;
окно не формирует представление для приложения. Кнопки переключают команды,
а не страницы ответа; все 20
записей остаются в истории. По умолчанию показывается последняя команда,
выбор более старой сохраняется при новых обращениях. Служебные
секреты и внутренние адреса проходят обычную очистку публичной границы MCP.
Для `storybook_capture` журнал сохраняет метаданные и `captureId` без base64,
отдельно загружает PNG через авторизованную browser-сессию и показывает превью.

HTTP-приём записи журнала допускает до 8 МиБ в UTF-8 на запись, отдельно от
лимита 64 КиБ обычных управляющих команд. Размер проверяется и по заголовку,
и при чтении потока; превышение отклоняется целиком, без усечения ответа.

Статус сервера содержит requestJournal: состояния последних записей, размеры
входов и ответов в UTF-8 и последнюю ошибку приёма записи. Сводка не включает
содержимое ответов и доступна независимо от работоспособности окна журнала.
