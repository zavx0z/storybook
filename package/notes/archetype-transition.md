# Переход к границам Domain и Cluster

[Структурный стандарт](./draft-structure.md#определения) закрепляет согласованные
определения. Эта заметка связывает их с ещё необходимой работой над читателями,
сценариями и представлениями. Новые определения не означают, что текущий
исполняемый стандарт уже проверяет их.

<a id="открытые-решения"></a>

## Протоколы и границы подтверждения

Реализация использует существующий ambient namespace Contracts с ролями Input,
Output и Slots по применимости. Component и Container сохраняют один собственный
namespace; простой выводимый default без авторского контракта не получает
фиктивный файл. Domain публикует один протокол на вход среды — собственный либо
принадлежащий точно выбранной реализации. Default-делегирование сохраняет origin.

Для своих входов Domain использует contract/index.ts либо contract/<имя входа>.ts;
общие определения располагаются у своего владельца и связываются типами.
Число сред не служит самостоятельным доказательством предмета; одна реализованная
среда не требует фиктивного второго воплощения. Читатель показывает общие
использованные определения, а смысл сущности подтверждают её реальные сценарии.

Cluster публикует именованных участников, их namespace и свой общий namespace
в основном входе. Type-only подпуть ./contract предоставляет детям общее
соглашение без обратного runtime-импорта каталога. Читатель проверяет исходные
связи и native типовую совместимость; совпадение скопированных полей недостаточно.

Расширение протокола и принадлежность реального пакета проверяются отдельно.
Типовая совместимость не подтверждает все поведенческие гарантии группы.
Для ещё не рассмотренных пакетов ответственность и миграция не выводятся
автоматически из имени, числа файлов или результата одной структурной проверки.

## Что переносится и что сохраняет владельца

| Положение прежнего Domain | Целевой владелец |
| --- | --- |
| Группировка самостоятельных возможностей и организация доступа к ним | Cluster при наличии общего протокола |
| Именованное раскрытие возможностей участников | Cluster; точный API требует решения выше |
| Общий протокол группы и расширения участников | Cluster и компоненты соответственно; чтение принадлежит Contracts |
| Происхождение runtime-символов и публичность входов | Package, без копирования правил в Cluster |
| Происхождение общих и собственных типов | Contracts, без присвоения чужих деклараций |
| Общие правила одной сущности и реализации для сред | Domain |
| Отсутствие собственной runtime-реализации как доказательство Domain | Прежний структурный признак; новым определением не подтверждён |
| Запрет собственного контракта у фасада | Не переносится на Cluster и не ограничивает новые протоколы Domain |
| Identity, зависимости, состав и безопасность чтения | Package и Repo сохраняют свои нормы |

## Выполненный этап читателей и сценариев

- Package сохраняет документы каждого входа вместе с условиями; index больше
  не является единственным распознаваемым публичным входом.
- Contracts раскрывает исходную реализацию, протокол и условия каждого входа,
  проверяет расширения общего протокола и размещение типов всех сред совместно.
- Domain имеет пример web.ts/server.ts без общего index; Cluster — общий
  протокол и самостоятельного участника с расширением.
- Единый сценарий Package различает новые роли. Каталог без общего протокола
  не получает Domain или Cluster; переносимый Container сохраняет один индекс.
- Существующие проверки происхождения, безопасности, композиции и TODO сохранены.

## Оставшаяся интеграция

Discovery, сериализация, выдача через MCP и представление двух средовых входов
ещё требуют согласованного обновления. Доступ Cluster адресному агенту пока
не изменён. Текущие читатели не являются доказательством готовности этой выдачи.
Все существующие пакеты Storybook и UI/Nodes в Immersive предстоит проверить
новым нормативным сценарием и их собственными сценариями, с исправлением
подтверждённых несоответствий и последующей совместной проверкой в Storybook.

## Последовательность и критерии

1. Уточнять конкретные публичные границы на малых проверяемых примерах.
2. Переработать факты входов, документации и контрактов. Для Domain без индекса
   должны сохраняться оба входа, условия, одна реализация и протокол каждого.
   Читатели не исполняют исследуемый код.
3. Добавить Cluster и переработать Domain в едином сценарии Package.
   Проверять общий протокол и происхождение расширений; реэкспорты сами по себе
   не подтверждают смысловой архетип. Второй классификатор не создаётся.
4. Перенести каталоговые примеры и полезные проверки к соответствующим владельцам.
   Отдельно сохранить положительный переносимый Container с одним индексом.
5. Обновить Discovery, сериализацию графа и ревизий, выдачу документации через MCP
   и доступ адресного агента. Источник, условия и протокол каждого входа не теряются.
6. Проверить ограниченный набор представителей и прямых потребителей.
   Отсутствующий протокол, лишняя реализация, закрытый импорт, несовместимое расширение
   и неоднозначный запрос входа получают собственные отрицательные примеры.
7. Отдельно спланировать миграцию реальных пакетов по ответственности и поведению.

Структурное чтение, типовая совместимость, поведенческий сценарий и проверка
штатного разрешения в реальной среде подтверждают разные свойства.
Браузерный и серверный графы проверяются отдельно. TODO и строгие assertions
не удаляются ради успешного отчёта; неизвестность не становится подтверждением.

Корневой launcher Repo, перенос App, реализация Chat, миграция Immersive
и приведение Cosmos к стандарту не выполняются автоматически вследствие этой работы.
Миграция UI/Nodes и всех сущностей Storybook поручена отдельно в продолжении задачи.
