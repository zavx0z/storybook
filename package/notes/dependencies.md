# Доступность зависимостей и контрактов

Потребитель импортирует контракт или реализацию непосредственно из публичного
API владельца. Публикация через реэкспорт не меняет этого владельца.
В Cluster ребёнок зависит от общего протокола самого кластера и сохраняет
собственный протокол с расширениями. Форма публичного доступа к общему протоколу
ещё [уточняется](./archetype-transition.md#открытые-решения);
типовая зависимость не превращается в runtime-импорт.
Состав и использование не смешиваются.

Import type стирается из JavaScript, но публичный тип может требоваться
TypeScript потребителя. Поэтому одно наличие import type не означает devDependency.
Dependencies нужны потребителю пакета; peerDependencies выражают совместимость
с общей библиотекой окружения; devDependencies обслуживают разработку владельца.
Optional dependencies сохраняют своё штатное значение. Поля typeDependencies нет.

Публичный реэкспорт не может полагаться только на devDependency, которая не
поставляется потребителю. У внутреннего типа, отсутствующего в поставляемом API,
может быть devDependency. Совместная установка монорепозитория не доказывает
переносимость отдельного пакета. Не вводится универсальное правило peer на Domain
или dev для всех типов.

Структурный сценарий проверяет объявление прямых зависимостей и публичных
реэкспортов; runtime импорт требует dependencies/peerDependencies/optionalDependencies.
Если карта exports владельца ещё не раскрыта читателем, публичность остаётся
непроверенной с TODO, а не превращается в установленное нарушение или успех.
Полноту публикации транзитивных объявлений и фактическую работу
во внешнем проекте подтверждает интеграционный пример владельца, а не имя поля.
Типовые и runtime-циклы различаются; сам факт реэкспорта домена ещё не создаёт цикл.
