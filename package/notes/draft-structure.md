# Единая структура Project, Repo, Domain, Cluster, Container и Component

Project владеет собственным Git superproject: имя берётся из его `package.json#name`,
состав независимых Repo — из `.gitmodules`, закреплённые версии — из gitlinks.
Отдельный сохраняемый список выбранных репозиториев не создаётся.
Repo сам является Package — корнем репозитория с собственной Git-историей.
Внутри него самостоятельные части выражаются пакетами следующих архетипов.

## Определения

**Component** предоставляет самостоятельную возможность через одну основную
реализацию и её публичный протокол. Он владеет поведением этой возможности,
может использовать внешние зависимости и содержать частные вспомогательные модули.

**Container** соединяет принадлежащие ему компоненты и вложенные контейнеры
в одно исполняемое целое. Он определяет совместную работу частей и предоставляет
собственную реализацию и протокол целого через единственный индексный вход.
Эта реализация может работать в одной среде либо быть переносимой между несколькими.

**Domain** объединяет общие понятия, правила и логику одной предметной сущности
с её реализациями для поддерживаемых сред. Каждая среда получает собственный
публичный вход, предоставляющий одну основную реализацию и соответствующий
протокол. Средовые реализации могут состоять из компонентов и контейнеров;
общий индексный вход домену не обязателен.

**Cluster** объединяет самостоятельные компоненты в смысловую группу,
принадлежность к которой определяется общим протоколом. Кластер владеет этим
протоколом и общими требованиями к участникам. Каждый компонент сохраняет
собственную реализацию и свой протокол, который соответствует общему и может
расширять его своими особенностями.

## Принадлежность и публичная граница

Один Repo может участвовать в нескольких проектах с сохранением собственной
identity и истории. Самостоятельные Repo не вкладываются друг в друга;
Repo располагаются внутри Project. Workspaces объявляет только Repo:
корневые glob охватывают его пакеты, а не Repo всего Project.
Вложенные пакеты не повторяют эти объявления.

Физическая вложенность выражает принадлежность, а использование через импорт
не передаёт владение. Число файлов, вложенных пакетов, реэкспортов и потребителей
само по себе не определяет архетип. Частные helpers не создают самостоятельных
частей композиции. Реэкспорт сохраняет владельца исходной реализации и типов.

Для Container существенна совместная работа принадлежащих частей.
Для Domain — общие правила одной сущности и их средовые реализации.
Для Cluster — общий протокол самостоятельных участников и соответствие ему.
Переносимый Container сохраняет один индексный вход и не становится Domain
только из-за поддержки нескольких сред. Каталог реэкспортов сам по себе
не подтверждает ни Domain, ни Cluster.

## Правило и выполненная проверка

Классификация не задаётся полем `kind` или `category`, именем папки или иконкой.
Единственной нормативной точкой проверки остаётся
[сценарий Package](../reader/spec/scenario.spec.ts): факты читателей,
условия применимости, утверждения и результаты одного запуска служат
проверке, документации, представлению Storybook и сведениям MCP.
Второй классификатор рядом с ним не создаётся.

[Сценарий Package](../reader/spec/scenario.spec.ts) проверяет новые роли:
средовые входы и протоколы Domain, общий протокол и расширения Cluster,
одну реализацию Component и исполняемую композицию Container.
Кандидат не подтверждается одним структурным признаком.
[Переход к проверяемому стандарту](./archetype-transition.md) отделяет выполненный
этап читателей от ещё необходимых миграций и проверки представлений.

Общие структурные проверки не копируются в каждый пакет. Поведение целого,
общие правила сущности, соблюдение протокола группы и особенности участников
проверяются у соответствующих владельцев. Читатели собирают факты без исполнения
исследуемого кода; наличие сценария не заменяет результат его выполнения.

Предмет архетипа и класс читателя различаются: `readDomain` — Component,
исследующий сведения о Domain. Файловая проверка не доказывает полноту смысла
предметных правил. Нереализованные проверки сохраняются
[у Component](../../component/notes/verification.md).

## Поэтапный переход

Существующие пакеты и пути не перемещаются автоматически вследствие уточнения
стандарта. Каждый пакет оценивается по ответственности и поведению.
Историческая Category сохраняет полезный смысл группировки равноправных частей;
Cluster уточняет его общим протоколом. Entity и Category не восстанавливаются
как структурные классы; обычные директории остаются
[переходным представлением](./draft-projections.md).

Несоответствие переходного пакета публикуется как предупреждение.
Полное прохождение стандарта и успешное применение той же ревизии закрепляют
строгий режим; последующая регрессия не переводит пакет назад в переходный режим.
Сохранением этого факта владеет lifecycle сборки, а не авторские metadata.
Исполнение сценария не меняет режим или файлы проверяемого пакета.
Технический отказ не становится успешной проверкой.
