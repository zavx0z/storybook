# Подготовка и применение ревизий пакета

Реализация: [сессия пакета](../index.ts) и [менеджер сессий](../../../app/server/sessions/index.ts). Подготовка принадлежит [сборке](../../../app/web/build/notes/compilation.md), применение внутри страницы — [runtime](../../../tech/hmr/notes/updates.md).

## Самостоятельная сессия пакета

Каждый package имеет собственные compiler context, module graph, generated
entry, ревизии, диагностику и подписчиков. Явный check подготавливает кандидата;
`check(live:true)` проверяет его identity, готовность, кадр и новые ошибки console
в открытых представлениях, затем подтверждает activation lease.
Обычный переход читает доступную ревизию. При её отсутствии навигация
запрашивает подготовку; независимая browser inspection подтверждает первый
кандидат перед закреплением рабочей версии. Явный preview не публикуется.
`check(live:false)` сохраняет кандидата для проверки без применения.

Явная сборка через `build()` всегда подготавливает нового кандидата. Одновременные
запросы разделяют уже исполняемый заказ; последовательный запрос запускает новую
подготовку даже при неизменных исходниках. `ensureBuilt()` обслуживает открытие:
использует подготовленную ревизию и заказывает сборку, когда её нет. Подписка и
чтение состояния не создают отдельную работу.

Успешный результат относится к выполненной сборке. Изменение исходников во время
или после неё не отменяет готовый артефакт и не подменяет его ошибкой свежести.
При следующем явном запросе строится новый кандидат. Обновление каталога через
`reconfigure()` сохраняет дескриптор для следующего явного заказа. Уже исполняемая
сборка завершается по своему снимку и публикуется один раз; открытие продолжает
использовать подготовленный результат.

## Сохранение рабочей версии

После пересоздания package scope для проверки кандидата первое сообщение
package.applied-state о прежней рабочей ревизии не заменяет кандидата.
До подтверждения новой версии scope сохраняет состояние navigation-candidate;
package.updated по-прежнему подтверждает применение или передаёт новое обновление.
Регрессия проверяется в runtime/package-entry.test.ts.

Failed build/activation сохраняет active/lastWorking artifact и immutable graph
snapshot применённой ревизии; server продолжает работу. Текущий canonical catalog
актуализируется перед сборкой и сохраняет результат обнаружения независимо от
исхода кандидата. Ошибка кандидата не заменяет рабочие артефакты других пакетов.
Без lastWorking только affected preview показывает isolated error.
После исправления явный live-check применяет
новую revision. Применение атомарно сохраняет private receipt и артефакт; после
перезапуска восстанавливается та же версия без чтения исходников. Receipt v1/v2
восстанавливаются по identity, графу, точному пути и наличию опубликованного
артефакта. Свежесть исходников не участвует в восстановлении. Неприменённый
кандидат не становится lastWorking при восстановлении.

При переносе пакета с сохранением его identity прежнее свидетельство проверяется
до восстановления. Смена физического корня не восстанавливает старую ревизию
как active или lastWorking: следующая явная проверка строит нового кандидата.
Достигнутый строгий режим сохраняется. Старые исходники при этом не читаются;
повреждённое свидетельство не допускается к пассивному открытию. Явная сборка
может подготовить нового кандидата с сохранением известного строгого режима;
прежние артефакты и receipt сохраняются до успешного применения нового результата.

## Изменения зависимостей

Состав ресурсов страницы обновляется по актуальному содержимому владельца,
даже если дерево пакетов и digest графа не изменились. Добавление или удаление локальной ссылки обновляет
дескриптор сборки, список копируемых ресурсов и входных файлов. При переносе
сведений между исходниками удалённый файл не остаётся обязательным входом следующей сборки.
Изменение только дескриптора создаёт новую ревизию реестра для синхронизации сессий,
не подменяя его изменением графа. Неизменившийся состав не создаёт новую ревизию.
Регрессия проверяется в `catalog/registry-resources.test.ts`.


## Граф применённой ревизии

Published revision содержит immutable package graph/route/resource snapshot.
Содержимое package tab использует только snapshot своей revision. Общее дерево
оболочки сохраняет положение пакета из текущего каталога по
[правилу дерева навигации](../../../app/web/page/shell/workbench/notes/workspace.md#дерево-навигации); его содержимое и маршруты берутся из применённой ревизии.

## Срок хранения артефактов

Retain active, lastWorking and leased revisions plus bounded recent history.
Capture store bounded by count/TTL; resource URI survives MCP client process
without exposing filesystem paths.

## Проверки поведения

Persistent fixture packages A/B/C доказывают one-origin session isolation:
A-only update не rebuild/reload B/C, shared A+B dependency не затрагивает C,
failed A сохраняет lastWorking и diagnostics, исправление публикует новую
revision. Consumer boundary scan проверяет отсутствие зависимостей, импортов
и обёрток Storybook в потребителях. Маршрутные проверки подтверждают адреса
физических пакетов и директорий; отдельные таблицы прежних историй не задают маршрут.

## Подтверждение строгого режима

[Состояние стандарта](../../standard/index.ts) связывает нормативный отчёт сценария
с конкретной ревизией. Новый пакет переходный. Полностью успешная проверка
и отсутствие предупреждений позволяют повысить его до строгого только при
успешном acknowledgement той же activation lease. Подготовка кандидата,
просмотр preview, ошибка применения и незавершённые требования не повышают режим.

Режим, сводка проверки и применённая ревизия записываются одним atomic rename
в applied.json. После перезапуска строгий режим сохраняется, даже если исходники
изменились или формат артефакта требует новой сборки. Регрессия оставляет прежнюю
рабочую версию и блокирует следующего кандидата. Повреждённое свидетельство
не даёт автоматически вернуться к переходному режиму. Авторский package.json
не содержит миграционных флагов.

Ранее сохранённый standard сохраняется независимо от прежнего поля assessment.
Оно не используется как подтверждение новых проверок; новую сводку verification
пакет получает из единого нормативного сценария.
