# Проверяемый архетип пакета: аудит и порядок перехода

Исследование 24 сентября 2026 года относится к каноническим checkout Storybook,
WebXR, Renderer и MetaFor. Это запись основания и этапов работы. Нормы остаются
у [Package](../archetypes/package/index.ts),
[размещения сущностей](../archetypes/entity/notes/draft-placement.md) и
[документации](../archetypes/notes/draft-documentation.md).

## Наблюдаемая структура

Обследованы обычные `.storybook/manifest.json` четырёх репозиториев без перехода
по symlink, без fixtures, node_modules и прежнего дерева projects. Все найденные
исполняемые декларации используют package-owned runtime и catalog; корень
Renderer служит композицией. Наличие декларации не является доказательством
запущенной или визуально принятой страницы.

| Владелец | Декларации | Наблюдение для стандарта |
| --- | --- | --- |
| Storybook | Корневой пакет | 13 категорий, 14 subjects; внешнее средство просмотра |
| WebXR | UI, Markdown, renderer/html, Nodes, Tree, Layout, Parameters, Sockets, Node | Пакеты имеют разное число компонентов; существующая структура не подтверждает правило «один компонент — один пакет» |
| Renderer | Корень, packages/core, packages/dom | Корень объединяет владельцев; кодовые exports указывают также на src и служебные модули |
| MetaFor | types, quantum/bulk | Пакет типов и пакет с состоянием/браузерным проявлением требуют разных проверок поведения |

Три показательных источника:

- `archetypes/package`: прежний readPackage читал только package.json, а сценарий
  проверял toBeDefined; readme/index оставались пустыми каркасами.
- `app/index.ts`: createScenarioApp удерживает состояние, предоставляет методы,
  подписку и dispose. app/package.json публикует компоненты и contract-файлы;
  описание description отсутствует. Это наблюдение, а не выбранный эталон.
- `webxr-space/nodes/node/package.json`: несколько JSX-компонентов и прямые
  exports contract/shared. Это реальные расхождения с существующим правилом
  публичного входа, а не основание переносить устройство Node во все пакеты.

## Ответственность и незавершённые решения

Проверяемая общая граница: пакет объявляет имя и API и владеет их исходниками;
Archetypes читает факты и исполняет спецификации; внешний Storybook представляет
те же данные человеку и агенту. Схемы состояния компонентов не принадлежат Tree
и не должны выводиться из его строк или подписи.

Последнее направление Владимира: компонент пакета владеет порядком pipeline,
состоянием, методами и подписками; функции обогащения дополняют переданный $
данными и не добавляют методы/подписки. Мутация аргумента не является чистым
вычислением. Историческое мартовское правило помещало мутации в главный модуль
пакета; окончательное размещение таких функций и Store ещё требует уточнения.

Не утверждены общая миграция каждого компонента в пакет, новая роль src,
единственное время жизни Store, окончательные имена полей lazy MCP. Наличие
index и contract-файлов не доказывает единственную исполняемую сущность,
смысловую полноту типов, корректность lifecycle или отсутствие скрытых эффектов.

## Этапы

1. Чтение непосредственного README и публичных входов. Сценарий Package применён
   к собственному пакету и принимает внешний props.path. Отсутствующие, чужие
   и непроверенные цели видимы. Файловые требования имеют настоящие проверки;
   семантические границы явно отмечены как todo.
2. Уточнение функций, компонента и Store на браузерном и серверном примерах.
   Согласованный закон размещения меняется у владельца; затем добавляются
   поведенческие примеры мутации данных, подписок и завершения работы.
3. Миграция одного компонента и одного серверного владельца по тому же закону.
   После проверки общего случая — отдельные порции для остальных пакетов.
4. Определение lazy MCP по смыслу пакета и его документации. Tree и MCP читают
   одну структуру; формат не выводится из query-параметров интерфейса.

Исполняемый первый этап находится в
[сценарии пакета](../archetypes/package/spec/scenario.spec.ts).
Дальнейшие этапы не считаются выполненными по результатам файловых проверок.
