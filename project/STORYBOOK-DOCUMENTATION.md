# Storybook как общая документационная среда

Эта заметка хранит ещё не перенесённый в код смысл и открытые вопросы. Действующие
правила находятся у [Archetypes](../package/src/architecture.md),
[владельца документации](../package/meta/notes/draft-documentation.md), в контрактах
и исполняемых сценариях. Заметка не задаёт отдельный протокол MCP.

## Единый источник

Владимир определил Storybook как одну документационную среду для человека и
агента. Пакеты и их код владеют содержанием; Storybook читает его и представляет
в одном Experience. Человек видит структуру, текст, примеры, средства управления,
media и результаты проверок через интерфейс. Агент должен получать сведения о
том же содержании и состоянии через MCP, без отдельного каталога знаний.

Структура пакета возникает из `package.json`, workspaces и публичных входов.
Назначение и поведение принадлежат TSDoc кода, `contract/index.ts`,
исполняемым `spec/scenario.spec.ts` и результатам сценариев.
README указывает путь к владельцу и ещё не перенесённым заметкам. Само наличие
файла или успешный тест структуры не доказывают смысловую полноту или визуальную
приёмку. [Порядок переноса заметок](../package/meta/notes/note-lifecycle.md)
определяет, когда временный текст можно удалить.

Storybook не владеет историями или правилами потребителей. Каждый общий факт
остаётся у своего пакета или общего владельца. Структурная проверка должна
обнаруживать отсутствие или неоднозначность обязательной связи, а не заменять
её параллельной ручной записью.

## Один предмет для человека и агента

Одинаковое восприятие не требует одинакового формата ответа. Визуальная кнопка,
структурное действие MCP и текстовое описание могут относиться к одному
элементу и состоянию. Для обеих сторон должны сохраняться владелец, положение
в структуре, текущий выбор, доступные направления и проверяемые связи с
исходником и сценарием. Точная форма будущего ответа MCP из этого принципа не
следует.

Пользователь понимает текущую область по её месту в структуре и видимым
соседним направлениям. История переходов для этого не нужна. Агенту достаточно
ограниченного текущего среза: содержимого выбранного направления и коротких
описаний доступных следующих шагов. Полное содержимое других ветвей и тяжёлые
артефакты можно раскрывать по запросу. Такой semantic viewport остаётся
направлением исследования, а не утверждённой схемой wire-полей.

Сейчас команда среды `knowledge.read` принимает необязательный `path`.
Корневой ответ и выбранное направление содержат `description`, `children` и,
когда полезно, `label`; адрес ребёнка передаётся как `path` следующего вызова.
Адрес выбирается из публичных направлений каталога. У выбранного владельца
ответ также раскрывает доступные входной и выходной контракты как JSON Schema
и исходный код сценариев. Это подтверждено
[входным контрактом](../app/knowledge/contract/index.ts),
[составом команд среды](../app/environment/index.ts) и
[сценарием навигации](../app/knowledge/spec/scenario.spec.ts). Среда передаёт
предметный JSON без собственного перечня полей ответа. Этот вызов не исполняет
сценарии и не возвращает отчёт их проверки.

## Поступательное раскрытие

Потенциально полезный порядок: короткое описание доступного направления,
выбор пакета, затем чтение нужного контракта, примера, источника, результата
проверки или media. Объём ответа должен оставлять агенту понятный следующий
шаг без угадывания внутренних URL или названий файлов. Структурные дети,
содержимое документа и технический способ показа следует различать по смыслу.
Имена новых операций и полей для дальнейшего раскрытия ещё требуют согласования;
действующий вход описан в контрактах выше.

Сравнение с Interpreter дало две идеи, а не готовый протокол для Storybook:
ограниченный поиск перед подробным чтением и загрузку данных точного узла при
раскрытии. Для длительной операции полезно различать загрузку, готовность и
ошибку, а также не применять запоздалый ответ к обновлённому состоянию.
Interpreter использует собственную предметную модель; её имена и формат не
становятся контрактом Storybook.

Чтение документации, запуск примера и изменение его состояния имеют разные
последствия. Будущий MCP должен делать это различие понятным агенту. Доступность
сведений сама по себе не разрешает воздействовать на работающий пример.

## Содержание и свидетельства

Исходник, сценарий, входные данные и результат проверки принадлежат своему
пакету. Storybook показывает их связь, но не объявляет компонент принятым на
основании одного снимка. Для media нужны различимые оригинальный артефакт,
авторское описание, технические параметры снимка и происхождение оценки.
Когда описание генерируется, его происхождение должно быть видно. Решения о
формате media, связях evidence и критериях приёмки остаются открытыми.

При неизвестном пакете или неоднозначном владельце полезнее явная ошибка,
чем догадка и переход к чужому содержимому. Ошибка сборки должна сохранять
наблюдаемую последнюю рабочую ревизию по действующему жизненному циклу
Storybook; свежесть конкретного документа агенту ещё предстоит выразить
понятным способом.

## Чтение из кода

[readPackage](../package/index.ts) возвращает метаданные, модульный
TSDoc корневого index и публичные входы с известными контрактами. Тот же
[читатель TSDoc](../package/documentation/index.ts) используется
обнаружением; README и заметки не читаются для заполнения этих сведений.
Отсутствие модульного описания сохраняется как отсутствие, код не исполняется.
`label` необязателен. Поиск допускает только виды действующего структурного графа.

Публичный `storybook({path})` возвращает навигационные метаданные, переходы,
доступные схемы контрактов и исходники сценариев выбранного владельца.
Подготовленное [представление выполненного сценария](../specs/presentation/meta/notes/presentation.md)
остаётся внутренним и не подключено к этому входу. Его развитие требует
согласования по фактическим результатам чтения кода.
Смысловая полнота описаний, контрактов и сценариев проверяется отдельно от
наличия файлов и успешного извлечения TSDoc.

## Открытые вопросы

- Какая минимальная часть текущего пакета нужна агенту для осмысленного выбора
  следующего направления без загрузки всего графа?
- Как связать публичный вход, TSDoc, контракт и сценарий с одним владельцем,
  сохранив понятную ошибку при неоднозначности?
- Как композиция нескольких репозиториев сохраняет точную принадлежность
  пакетов без второго реестра и копий документации?
- Какие данные сценария и результата проверки можно раскрывать независимо и
  как показать их свежесть без преждевременного утверждения нового wire-формата?
- Когда агенту нужен сам media artifact, когда авторское описание и как
  сохранять происхождение автоматически созданного описания?
- Как доказать на одном реальном пакете, что интерфейс и MCP раскрывают один
  смысл и предлагают понятный следующий шаг?
- Какая проверка позволит удалить временную заметку, не потеряв уникальный
  смысл, который пока не выражен у владельца?
