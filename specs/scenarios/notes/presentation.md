# Представление сценария и граница автора

Правила авторства находятся в [исполняемом руководстве](../spec/scenario.spec.ts).
Эта заметка связывает их с потребителями сценария и сохраняет сведения,
которые ещё не выражены полностью в коде.

## Граница ответственности автора

Автор, в том числе специализированный агент, пишет обычный сценарий на bun:test
и работает с публичным контрактом проверяемой функции или компонента.
Знание устройства Storybook, MCP и приложения для этого не требуется.
Эти сведения не входят в руководство по написанию сценариев и не должны
становиться обязательным контекстом автора.

Извлечение, кэширование и представление данных принадлежат потребителям сценария.
Они используют обычные describe, test и expect по согласованным правилам,
не требуя от автора отдельных деклараций для интерфейса или MCP.

Компонент объявляется JSX непосредственно в единственном аргументе `render`.
Нормативный пример и проверка — пункт «JSX непосредственно в render» руководства.
Извлечение этого JSX принадлежит читателю Specs, компиляция — Build; автор не создаёт
`Fixture` или `Example` для удовлетворения ограничений читателя.

## Общие и частные проверки

Порядок общих и частных проверок закреплён и проверяется в
[исполняемом руководстве](../spec/scenario.spec.ts), пункт «Общие и частные проверки».
Применимость частной темы выражается штатным `describe.skipIf`.

### Ориентир для будущей оценки архитектуры

Если частного поведения становится больше, чем общего, это признак
неправильно выбранной ответственности компонента или функции. При дальнейшем
развитии сценариев использовать это как повод пересмотреть границы компонента:
выяснить, какие самостоятельные ответственности объединены, и уточнить общий
контракт либо разделить самостоятельные компоненты по их назначению.

Оценка относится к смыслу и объёму поведения. Способ автоматической оценки
этого соотношения ещё не определён; заметка сохраняет ориентир для будущего
анализа структуры сценариев.

## Руководство по написанию сценария

Руководство объясняет автору расположение файлов и написание сценария через
исходный код настоящих примеров. [readScenarioGuide](../index.ts) принимает
`{path}` — путь к `spec/scenario.spec.ts` или `spec/scenario.spec.tsx`.
Чтение и запуск выполняет Specs. [Scenario Document](../../document/index.ts) определяет
соседние файлы владельца
и выбирает из полученного отчёта кодовые примеры и результаты проверок.
Вызывающий код не собирает отчёт или список файлов вручную.

Признак `scenario-guide` позволяет App показать это содержание как файлы и код,
сохраняя обычный JSON-просмотр для технических результатов функций.

Результаты функций, снимки аргументов, полный вывод Bun и JUnit остаются в
[техническом отчёте Specs](../reader/README.md). App может
показывать их подробно, а MCP — раскрывать по запросу. Отсутствие этих значений
в руководстве не скрывает провалы: `checks` различает успешную, нарушенную и
непроверенную проверку.

В `files` входят сам сценарий и существующие обычные файлы публичного входа,
контрактов и фикстуры этого владельца. Имена импортов не заменяют проверку
наличия файла. Правила смысловой достаточности примеров остаются открытыми
в [сценарии Archetypes](../spec/scenario.spec.ts).

## Предметный документ выполненного сценария

Публичный [readScenarios](../../presentation/index.ts) подготавливает JSON-документ с заголовком title, абзацами content
и вложенными sections. Каждая функция и каждый компонент используют одну
форму; содержание раскрывает их собственное назначение и поведение.

Варианты, категории и пункты становятся разделами. Их порядок сохраняется
по исходнику. Абзац связывает пояснение text с предметным значением value:
это может быть результат функции, свойство компонента или настоящий пример кода.
Имена полей тестового API не используются как ключи структуры документа.

| Источник | Документ |
| --- | --- |
| Название варианта, категории или пункта | Заголовок title |
| customFailMessage | Пояснение text в абзаце content |
| actual выполненного expect | Предметное значение value того же абзаца |
| Вложенность describe и test | Вложенность sections |

Условия matcher, координаты и технические состояния остаются в диагностике.
Неподтверждённые положения, неприменимые примеры и ошибки обозначаются заметками
notes, без выдуманных данных. Пустые предметные значения сохраняются; пустые
структурные списки не добавляются.

Содержание определяет автор сценария. Если actual содержит список нарушений,
он рассказывает о валидации. Для руководства нужны примеры и предметные данные,
которые раскрывают описываемый приём; одна замена имён ключей этого не обеспечивает.

Преобразование JSON принадлежит HTTP-обработчику, MCP остаётся непрозрачным
прокси. Полный технический отчёт принадлежит Specs, визуальное представление — App. Точный текущий формат
описан у [владельца представления](../../presentation/notes/presentation.md).

Подготовка и обновление данных описаны отдельно:
[Сборка и кэширование данных сценариев](../reader/notes/build-cache.md).
